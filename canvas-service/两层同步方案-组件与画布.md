# 产品工厂 → 画布系统：组件 / 画布 两层同步方案

> 生成日期：2026-08-29
> 背景：上一版把「画面组件」直接当成「画布」同步，导致画布列表臃肿且语义错位。本方案纠正为两层结构。

---

## 一、探查结论（事实依据）

### 1. 产品工厂的完整层级（运行时拼页面，库中只存组件）

```
产品 tb_prod_dfn_product（181 个，c_prod_no 唯一）
 └─ 页面 = 产品 + c_screen_content_type（1=投保 / 2=报价）   ← 不存库，运行时按 n_show_order 拼
      └─ 画面组件 tb_prod_rel_screen（7111 个，c_screen_no 全局唯一）  ← 库里最大粒度
           └─ 元件（两种存储，见下）
```

### 2. 关键事实

| 事实 | 数据 |
|---|---|
| 产品数 | 181 个（投保 181 / 报价 179） |
| 画面组件数 | 7111 个（投保 3567 / 报价 3544） |
| `c_screen_no` | **产品专属**（每个 screen_no 只属 1 产品 + 1 页面类型，跨产品不复用） |
| 页面组织 | 按 `c_prod_no + c_screen_content_type` 分组，组内按 `n_show_order` 排序 |
| 元件存储 | **两代架构**：车险(05 险类, 6 产品) 内嵌在 `c_screen_json.formFields`；其他 175 险种在 `tb_prod_screen_rel_elem` 表 |

### 3. 车险 JSON 结构（`c_screen_json.formFields[]`）

以画面 `063148 基本信息`（109KB）为例，每个 formField 的字段（驼峰命名，与 elem 表的 c_ 前缀不同）：

```json
  "mustInputFlag": "1", "readOnlyFlag": "1", "viewShowFlag": "1",

  "checkType": "1", "contrlAttr": "", "compCode": "C05110",
  "title": "", "dateFormat": ""
}
```

### 4. 非车险元件的字段（`tb_prod_screen_rel_elem`，c_ 前缀，与车险 JSON 不同）

`c_elem_no / c_elem_cname / c_contrl_type / c_rel_field_name / c_rel_table_name / c_must_input_flag / c_read_only_flag / c_view_show_flag / c_status / c_default_value / n_mini_value / n_maxi_value / n_precision_val / c_codelist_id / n_string_length / c_check_type / c_contrl_attr / c_comp_code / c_title ...`

## 二、两层映射方案

### 层 1：画面组件 → 组件（tb_element_group）

| 产品工厂字段 | 组件字段 | 说明 |
|---|---|---|
| `c_screen_no` | `c_group_code` | 组件代码（唯一） |
| `c_screen_cname` | `c_group_name` | 组件中文名（"投保人信息"） |
| `c_screen_ename` | `c_group_desc` 或保留 | 组件描述 |
| `c_screen_content_type` | `c_group_type` | 1=投保组件 / 2=报价组件 |
| 元件的 `n_elem_show_seq` | elements[]._rowIdx/_colIdx | 组件内布局位置 |
| 画面内所有元件 | `c_elements_json` = `{columns, elements[]}` | 组件内容 |

**元件来源（分代处理）**：
- 非车险：`SELECT * FROM tb_prod_screen_rel_elem WHERE c_screen_no = ?` 按 `n_elem_show_seq_no` 排序
- 车险：解析 `c_screen_json.formFields[]`，字段映射见第三节

### 层 2：产品页面 → 画布（tb_canvas）

| 来源 | 画布字段 | 说明 |
|---|---|---|
| `c_prod_no + "_" + c_screen_content_type` | `c_canvas_code` | 如 `05001_1`（投保）、`05001_2`（报价） |
| `c_prod_name + "投保/报价"` | `c_canvas_name` | 如「机动车商业保险-投保页」 |
| 固定 `form` | `c_canvas_type` | 页面类型 |
| `c_screen_content_type` | 存画布 JSON 的 `contentType` | 区分投保/报价 |
| 该产品该类型下所有画面组件（按 n_show_order） | `c_canvas_json.items[]` | 每个 item 引用一个组件 |

**画布 JSON 结构**（items 引用组件，符合前端 `setFromCanvas` 的 component item 格式）：

```json
{
  "canvasType": "form",
  "contentType": "1",
  "columns": 1,
  "items": [
    { "itemType": "component", "refCode": "063150", "refName": "车辆信息", "compColumns": 1, "childElements": [...] },
    { "itemType": "component", "refCode": "063148", "refName": "基本信息", ... }
  ]
}
```

> 每个 component item 的 `refCode` = 组件代码（c_screen_no），`childElements` 为组件内元件明细。

## 五、组件去重策略（已定：方案 C）

### 探查结论（同名组件的元件同构度）

以「投保人信息」为例（181 产品 / 360 画面）：

| 指标 | 数值 |
|---|---|
| 单产品元件数 | 77（绝大多数），少数 78 |
| 所有产品元件并集 | 82 个 |
| 被 175 产品共用的元件 | 59 个（核心集） |
| 只被 2-4 产品用的差异元件 | 少数（如 E00219、B000001、E200007） |

**结论**：同名组件 = 核心元件集 + 少量产品差异。方案 C 落地：

- **组件层**：每个「画面名」生成 1 个标准组件，元件 = 核心集（被 ≥50% 产品共用的元件，按出现频次降序，取众数频次的前 N）
- **画布层**：每个产品页面引用组件时，`childElements` 带上该产品自己的元件明细（覆盖/补充标准组件的差异）

### 组件标准集的定义

对每个画面名：
1. 统计该画面名下每个 `c_elem_no` 出现的产品数
2. 标准集 = 出现产品数 ≥ 该画面名总产品数 50% 的元件（即核心集）
3. 元件排序按该画面名下的平均 `n_elem_show_seq_no`

## 六、实施结果（三层模型，已落地）

经双向同步约束分析，最终采用**三层模型**（而非两层「标准组件去重」）：

| 层 | 目标表 | 数量 | 关键映射 |
|---|---|---|---|
| 元件定义（全局模板） | tb_canvas_element（c_canvas_code=''） | 1383 | = c_elem_no 去重 |
| 组件（产品专属实例） | tb_element_group | 6958 | c_group_code = c_screen_no，c_group_tag = 产品号 |
| 画布（产品页面） | tb_canvas | 360 | c_canvas_code = 产品号_contentType，items 引用组件 |

**为什么组件是「产品专属实例」而非「标准去重」**：
- 产品工厂的 `c_screen_no` 是产品专属（每个 screen 只属 1 产品），同名画面是独立记录
- 若组件去重为全局模板，回写产品工厂时无法确定「改哪个产品的 screen」
- 组件 = 产品专属实例，保证画布→页面、组件→screen 一一对应，反向回写精确

**双向同步的映射（已对齐）**：
- 画布 items 的 component refCode = c_screen_no = 组件 code
- 组件 c_group_tag = 产品号，回写时定位产品
- 元件定义是唯一全局共享层，复用不产生回写歧义
